# Agro Vision Frontend - Reglas de Gobierno

### Section 1: Reglas Inviolables

1. **CERO `any`** — TypeScript en modo estricto (`strict: true`, `noImplicitAny: true`). Prohibido usar `any` o casteos inseguros como `as unknown as Type`.
2. **LÍMITE ESTRICTO DE 300 LÍNEAS** — Ningún archivo de código (`.ts`, `.tsx`) puede superar las 300 líneas. Todo componente, hook o contenedor que crezca debe modularizarse y descomponerse en submódulos o componentes más pequeños.
3. **CERO CONTEXTOS MANUALES PARA CACHÉ / DATOS REMOTOS** — Usar exclusivamente **TanStack Query v5** para Server State. Prohibido usar `React.createContext` con `useState` para sincronizar o almacenar datos de la API.
4. **LOS 4 CUADRANTES DE ESTADO** — 
   * **Server State:** TanStack Query v5 (consultas, mutaciones, invalidación de caché).
   * **Form State:** React Hook Form + Zod (validación tipada con mensajes de error en español).
   * **Global UI State:** Zustand v5 (sesión de usuario, tema, parcela activa).
   * **Local UI State:** `useState` / `useReducer` (modales, acordiones, estados efímeros de UI).
5. **MOBILE FIRST & MULTIPLATAFORMA (Android + Web)** — Todo componente visual debe diseñarse primero para pantallas móviles táctiles (Android) y escalar fluidamente a tablet y desktop (Web). Prohibido forzar scrolls horizontales o diseñar vistas que no se adapten a pantallas pequeñas.
6. **PATRÓN CONTAINER / PRESENTATIONAL** — Los componentes contenedores (`containers/`) orquestan datos, hooks y mutaciones. Los componentes presentacionales (`components/`) son funciones puras que solo reciben props y renderizan UI.
7. **PÁGINAS DEDICADAS EN LUGAR DE MODALES PESADOS** — Las vistas de creación, edición y detalle completo deben ser rutas dedicadas en Expo Router (`/modulo/nuevo`, `/modulo/[id]`, `/modulo/[id]/editar`). Los modales o bottom sheets quedan reservados exclusivamente para confirmaciones breves, filtros rápidos o selección de opciones.
8. **SKELETON SCREENS OBLIGATORIOS** — Prohibido usar spinners genéricos en pantallas completas o dejar pantallas en blanco durante la carga inicial de datos. Cada lista, ficha o tarjeta de datos debe contar con su componente Skeleton que replique la forma del contenido real.
9. **CERO HARDCODING Y CERO DATOS FICTICIOS EN CÓDIGO** — Prohibido crear valores simulados, listas, usuarios o catálogos quemados/hardcodeados en el código. Todos los datos que visualice o seleccione el usuario deben provenir dinámicamente de la base de datos a través de la API.
10. **SIN ATRIBUCIÓN IA** — No incluir firmas, encabezados ni comentarios del tipo "Generated by AI" o "Co-Authored-By AI".
11. **PATH ALIASES `@/*`** — Usar siempre alias de importación configurados en `tsconfig.json` (`@/features/...`, `@/shared/...`). Prohibido el anidamiento relativo profundo (ej. `../../../`). Solo se permite `./` para archivos hermanos directos.
12. **LENGUAJE UBICUO EN ESPAÑOL** — Módulos, carpetas, componentes, rutas de navegación, esquemas de validación y hooks DEBEN nombrarse en español canónico (`parcelas`, `cultivos`, `monitoreo`, `diagnosticos`, `autenticacion`, `perfil`). Estrictamente prohibido usar anglicismos en la estructura de negocio.
13. **ACCESIBILIDAD Y COPIABILIDAD EN CAMPOS DE SOLO LECTURA** — Los campos informativos (coordenadas, códigos de lote, métricas) deben ser seleccionables y legibles, con contraste adecuado tanto en modo claro como en modo oscuro.
14. **REUTILIZACIÓN OBLIGATORIA DE COMPONENTES UI** — ANTES de crear cualquier botón, tarjeta, badge, input o skeleton, verificar si ya existe en `@/shared/components/ui/`. Si un patrón visual se repite en 2+ módulos, debe abstraerse en el UI Kit compartido.
15. **APROVECHAMIENTO COMPLETO DEL ESPACIO EN WEB** — En pantallas de escritorio / Web (`width >= 980px`), las vistas, tablas y formularios deben ocupar todo el espacio disponible (ancho de trabajo fluido de hasta 1400px con distribución a 2 columnas o tabs estructurados). Prohibido encajonar formularios en contenedores estrechos centrados de 700-800px que desperdicien la pantalla y fuercen scroll vertical excesivo.

### Section 2: Commits y Colaboración

* **Formato:** `<tipo>(<modulo>): <descripción imperativa en español>` (máximo 72 caracteres).
* **Tipos permitidos:** `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`.
* **Unidades atómicas:** Código + tipos + esquemas + tests en el mismo commit.

---

### Section 3: Estándar JSDoc Exclusivo

* Usar exclusivamente bloques estructurados `/** ... */`. Prohibido el uso de comentarios dispersos `//` dentro del código.
* Explicar el **POR QUÉ** del componente o hook y su rol en la UI.
* Etiquetas estándar: `@description`, `@param`, `@returns`, `@example`.
* Idioma: Dominio y descripciones en español técnico, firmas de tipos en TypeScript estándar.

---

### Section 4: Pipeline de Validación

Antes de dar por completada una tarea o realizar un commit:

```bash
pnpm run lint

```
